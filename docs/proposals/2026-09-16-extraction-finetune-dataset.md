## 1. The claim the proposal got wrong

The self-hosting proposal (2026-09-15, line 94-96) says distillation data is

> *"a capture job rather than a labelling job — `usage.py` already instruments every
> prompt/response pair"*

**That is false, and the correction matters more than the wording.**
`src/graph_extract/usage.py:42-47` is the whole of `record`:

```python
def record(kind: str, *, prompt: int, completion: int, cached: int = 0) -> None:
    _TALLY.add(kind, prompt=prompt, completion=completion, cached=cached)
```

`prompt` and `completion` are **integers**. `_tally_usage` (`usage.py:50-64`) reads
`resp.usage` — token counts — and nothing else. `instrument` (`usage.py:67-93`)
wraps `chat.completions.create` and `responses.create/parse`, passing `*args,
**kwargs` (which carry `messages`) straight through without reading them.

A full sweep of the repo confirms no prompt or completion text is persisted
anywhere:

| surface | what it holds |
|---|---|
| `usage.py` | integer token tallies only (`UsageTally`, `:8-24`) |
| `llm_timing.py` | call counts + latency lists keyed by `prompt_name` (`:44-54`) |
| `dedup_guard.py` | holds full prompt text in memory (`:114`, `:224`) but discards it on return; its stats dataclass (`:56-81`) is all ints, its log lines (`:218`, `:251-257`) emit indices only |
| Neo4j | model-authored *parsed fields* (`Episodic.content`, `Entity.summary`, `RELATES_TO.fact`) — never a raw completion |
| Postgres | `state_store.py:14-38` — cursors, webhooks, dead letters, a token ledger. No prompt column |
| `.superpowers/sdd/*.log` | index lists and counters. Longest line across all six logs: 674 chars; the largest model-output fragment is graphiti's own `"LLM returned summary for unknown entity (first 30 chars): AWS Backup"` |
| HTTP logging | none configured — `OPENAI_LOG` appears nowhere, no httpx logger, no `event_hooks` |

The only `(prompt, completion)` pair effectively on disk is in
`docs/superpowers/slice-2b-quality-baseline.json`: 15 `raw_answer` strings from the
**type-precision judge** (`eval.py:455-457`), whose prompt is reconstructible from
`_TYPE_JUDGE_PROMPT` (`eval.py:356-363`). That is an evaluation prompt, not one of
the five extraction prompts, so it is worth zero to this fine-tune.

**Consequence:** this is a *labelling* job. The proposal's step 4 ("harvesting a few
thousand examples per prompt type ... is mechanical") is not true today. It becomes
true after ~2 h of instrumentation work — which is option B below.

### Update, 2026-09-17: the instrumentation was built, so the claim is true now

The capture wrapper landed (`36a0bf1` `feat(usage): opt-in JSONL prompt/response
capture at the instrument() choke point`, `b89eeaa` `feat(usage): tag capture
records with graphiti's prompt_name`, merged as `4094b61`) and the run described in
§2c executed. `usage.py` now *does* persist prompt/completion text —
`capture_llm_call` (`usage.py:159-207`) writes a JSONL record per call and
`_request_payload` (`usage.py:121-135`) captures `messages` (chat) or `input`
(Responses API) plus the schema kwarg.

Two things worth keeping straight, because "the proposal was right after all" is
the wrong lesson:

- It is **opt-in and off by default**. `instrument(..., capture_path="")` is the
  default and costs nothing: no file is opened and nothing is serialised
  (`usage.py:215`, `:232`, `:248`). The self-hosting proposal's claim was that capture was
  *already* happening; it was not, and it still is not unless a runner sets the
  path.
- `prompt_name` comes from `CURRENT_PROMPT_NAME`, a **ContextVar** set only by
  `dedup_guard`'s `generate_response` wrapper (`usage.py:48-62`). That is what makes
  the capture bucketable at all — without it every record would be an unlabelled
  blob and none of §2c's per-prompt numbers would exist. Call sites that do not go
  through graphiti's LLM client write `""`, deliberately distinct from
  `dedup_guard`'s `"unknown"`.

The table above therefore still describes the repo as it was on 2026-09-16, and the
"labelling job" conclusion still describes what had to be done. It just got done.

## 2. What data actually exists — the three options, priced

### Option A — reconstruct from the graph (**recommended**)

The live graph stores more than the proposal assumed. Measured read-only:

```
999 entities   655 episodes   3,590 RELATES_TO   4,479 MENTIONS   83 articles with episodes
Entity.name_embedding      999/999 populated, 768-d
RELATES_TO.fact_embedding  3,590/3,590 populated, 768-d
Episodic.content           655/655, 112–5,935 chars, mean 1,443
```

Three of those are decisive:

1. **`Episodic.content` is the exact prompt input.** `IngestDriver` calls
   `add_text_episode` once per chunk (`ingest_driver.py:191-194`), and graphiti's
   `concatenate_episodes` returns a single episode's content verbatim
   (`utils/text_utils.py:69-70`). So the `episode_content` slot needs no
   re-fetch. **DocExtractor is not needed at all** — contrary to the brief's
   framing, article text never has to be pulled back.
2. **`MENTIONS` and `RELATES_TO.episodes` give per-episode attribution**, so the
   targets for entity and relation extraction are recoverable per call.
3. **The stored embeddings reproduce graphiti's candidate ranking offline.** The
   same embedder wrote them during ingestion, so dedup candidate lists can be
   rebuilt with no embedder call and no cost.

**Cost: $0.00. Wall clock: 4 m 05 s measured** (`time` on the full build, one
command). Yield (printed by the builder):

| prompt | derivable | of which |
|---|---:|---|
| `dedupe_edges.resolve_edge` | 2,248 | 1,897 true negatives + 351 synthetic positives |
| `extract_nodes.extract_text` | 651 | all graph-derived |
| `extract_edges.edge` | 615 | all graph-derived |
| `extract_nodes.extract_summaries_batch` | 347 | all graph-derived |
| `dedupe_nodes.nodes` | 329 | negatives only |

**The honest loss.** The graph is the state *after* dedup and merging, and the loss
is not uniform — it is concentrated exactly where the brief warned:

- **`resolve_edge` and `dedupe_nodes` positives do not exist.** When graphiti
  resolves a duplicate it keeps the **existing** text and discards the newly
  extracted paraphrase. The string the model actually produced is gone. 1,232 merge
  events are visible in the graph (facts whose `episodes` list has more than one
  entry) but only as *events* — the text is unrecoverable. The negatives are fully
  faithful; the positives are structurally absent.
- **`extract_summaries_batch` has the weakest target in the set**, and is the
  smallest split for a reason. `Entity.summary` is the *final* summary after every
  later episode updated it, not the summary produced at the call being
  reconstructed, and the prior-summary state is unrecoverable, so the rebuilt
  prompt shows an empty existing summary. It is also the only prompt where the
  pipeline often makes **no LLM call at all**: `_extract_entity_summaries_batch`
  appends the node's edge facts to its summary and, when the result is
  `<= MAX_SUMMARY_CHARS * 2` (2,000 chars), assigns it directly and skips the LLM
  (`node_operations.py:880-882`). The builder replays that gate — which is why this
  split is 347 examples and not 655. Replaying it against the *final* summary
  over-admits slightly, and that is disclosed per record.
- **`extract_text` / `edge` names are post-dedup canonical names.** Where dedup
  merged an extracted name into an existing node, the target carries the survivor.
- **Candidate ordering is approximate.** Candidates are ranked by stored-embedding
  cosine and assembled in graphiti's own union order; graphiti's live ranking is
  hybrid fulltext+vector RRF. The candidate *set* largely overlaps, the *indices*
  can differ — which matters for an index-picking task.

Every one of these is recorded per record in `meta.fidelity`, so a reviewer sees the
caveat next to the example rather than only in this document.

### Option B — add capture instrumentation and re-ingest the 83 pilot articles — **DONE, see §2c**

Truthful pairs for all five prompts, **including the positives Option A cannot
produce**. The instrumentation is a near-copy of `dedup_guard.install_dedup_guard`
(`dedup_guard.py:187-261`): wrap `graphiti.llm_client.generate_response`, write
`(prompt_name, messages, response)` to JSONL. It already keeps a `pristine` copy of
the messages at `:224`.

- **Cost: ~$10** — 83 articles × ~$0.12/article blended across both tiers
  (2026-09-15 proposal, line 101; the only measured per-article figure in the repo).
- **Wall clock: 2 h 10 m at N=4, 6 h 55 m sequential** (`ab-w8-validation.py:5-6`).
- **Dev: ~2 h** for the capture wrapper and a runner.
- **Risk:** it writes to the graph. It must use the established supersede-and-restore
  method (`ab-w8-validation.py:11-13`, `ab-revert.py`) and **never** reset the
  semantic layer — the 999-entity graph is the project's only reference copy.
- **Requires explicit authorisation** (money + a run of the ingest path the brief
  forbids by default).

### Option C — distil from the strong tier (`gpt-5-mini`)

Highest-quality targets, and the only option that can *exceed* the current teacher.

- **Cost: not derivable from anything recorded here.** The repo has no price table
  (`cost_report`, `eval.py:213-242`, reports tokens, not dollars) and the $0.12
  figure is blended across tiers, so it cannot be split. **[estimate]** a
  strong-tier-only pass over the same 83 articles is 2–4× the blended figure,
  i.e. **~$20–40** — but that is a guess and should be replaced by a priced probe
  on ~2 articles before anything larger is launched, per the standing cost rule in
  CLAUDE.md.
- **Requires explicit authorisation.**

### Recommendation

**Build from the graph now (A), and treat B as the targeted follow-up that buys the
one thing A structurally cannot: true index-picking positives.** A is free, is
already done, and covers ~90% of the prompt surface faithfully. B costs ~$10 and
fixes the specific hole. C is not worth its price until A+B have been measured,
because its advantage is quality headroom on a task where the binding constraint is
format, not comprehension (§5).

**Outcome: B was authorised and executed on 2026-09-17.** The recommendation held —
B bought exactly the hole A could not fill, and rather more besides. §2c is the
result. The graph-derived path in the builder is unchanged and still runs; it is now
the *cross-check*, not the dataset.

## 2b. Four defects found in review, and what they cost

The builder was reviewed against graphiti's source after it first ran clean. Four
real defects came out of that, all of which produced *plausible-looking* data rather
than errors. Recording them because each one is a way this kind of reconstruction
fails silently:

1. **`as_datetime` dropped the timezone.** A "keep the digit characters" filter ate
   the digits out of the UTC offset as well as the fractional seconds, yielding a
   *naive* datetime. graphiti's `EpisodicNode.valid_at` is tz-aware, and `str(dt)`
   on a naive datetime omits the `+00:00` that production renders into
   `<REFERENCE_TIME>`. **My own fidelity harness could not catch this**, because it
   built its EpisodicNode from the same converted value — a circular check. It is now
   asserted against the neo4j driver's native `to_native()` conversion instead:
   655/655 equal. On a `-05:00` input the old code also mis-parsed the fraction
   (120500 µs instead of 120000).
2. **`resolve_edge` grouped facts by an *undirected* node pair.** graphiti's
   duplicate candidates come from `EntityEdge.get_between_nodes`, whose Cypher is
   directional: `(n {uuid:$source})-[e:RELATES_TO]->(m {uuid:$target})`
   (`edges.py:421-423`). The undirected grouping showed the model B→A facts that were
   never in `EXISTING FACTS`, and mislabelled as "negatives" facts whose real
   candidate list was empty — where `edge_operations.py:653` issues **no LLM call at
   all**. Cost: 86 fabricated records (1,983 → 1,897).
3. **The summary-batch LLM gate was not replayed** (see §2). Cost: 308 records — 47%
   of that split — described calls that never happened.
4. **`dedupe_nodes` candidates were re-sorted by `created_at`**, destroying the
   similarity order `_merge_candidate_nodes` produces (`node_operations.py:387-404`)
   and renumbering every `candidate_id`. This also contradicted the builder's own
   `meta.fidelity` note, which claimed cosine ordering.

A fifth reported issue — the missing `**candidate.attributes` spread in
`existing_nodes` (`node_operations.py:519-528`) — was checked and is **not** a defect
here: no entity type in `ontology.py` declares attributes (deliberately, so graphiti
skips attribute extraction entirely), and the live graph confirms it — `Entity`
property keys are exactly `created_at, group_id, labels, name, name_embedding,
summary, uuid`. `candidate.attributes` is `{}`, so the spread is a no-op. It would
become a real gap the moment an attribute is added to any entity type.

## 2c. The capture run — what it produced, 2026-09-17

The authorised capture run wrote **4,743 `(prompt, completion)` pairs, 64.6 MiB**,
covering all five extraction prompts over the same 83 pilot articles. The graph was
reverted afterwards and re-verified read-only at the baseline (999 / 655 / 3,590 / 0
superseded / 83 articles), so nothing below cost anything to compute: the rebuild is
offline JSONL processing plus read-only Cypher.

```
dedupe_edges.resolve_edge               2647        (cheap 2324 / strong  323)
extract_nodes.extract_text               655        (cheap  613 / strong   42)
extract_edges.edge                       655        (cheap  613 / strong   42)
dedupe_nodes.nodes                       524        (cheap  487 / strong   37)
extract_nodes.extract_summaries_batch    262        (cheap  242 / strong   20)
```

655 each for `extract_text` and `edge` is exactly one per episode, which is the first
confirmation the capture is complete rather than sampled.

### The strong-tier records are excluded by default, and that is a decision

464 of the 4,743 records are `gpt-5-mini` on the Responses API, not `solar-pro4`.
Measured: **6 of the 83 articles routed entirely to the strong tier, 77 entirely to
the cheap tier, and zero articles were mixed** — so the hybrid router's decision is
per-article, as designed. Two reasons `--capture-tier` defaults to `cheap`:

1. The fine-tune replaces the **cheap tier**. For the three extraction prompts the
   strong tier renders `EXTRACTION_INSTRUCTIONS` *without* `CHEAP_TIER_SALIENCE`
   (`cli.py:117` appends it to the cheap tier only, and `ontology.py:143-145` says
   not to add it globally). Training on those prompts is the train/serve mismatch §4
   exists to avoid.
2. A strong-tier "completion" in the capture is not raw text: the Responses-API
   branch records `parsed.model_dump_json()` (`usage.py:138-150`), i.e. a
   re-serialisation, so its provenance is weaker than the cheap tier's even though
   its content is better.

`--capture-tier both` includes them if you disagree; nothing else changes.

### Problem 1 — attribution, solved at 96.5%

Capture records carry **no `article_id` and no `episode_uuid`**, and the split is by
article on purpose (§8). Attribution had to be recovered offline. Four of the five
prompts embed `episode_content` verbatim, so they match an `:Episodic` node by
content and inherit its article — and the match is clean: 655 episodes, **655
distinct contents, no collisions**.

`dedupe_edges.resolve_edge` embeds no episode content, only the NEW FACT text. The
brief suggested joining it to `RELATES_TO.fact`. **That route was measured and is
mostly a dead end:** on the 2,324 cheap `resolve_edge` records, matching NEW FACT
against the graph attributes **347 (14.9%)** — 1,897 (81.6%) of the NEW FACT strings
are *not in the graph at all*, because they were merged away or dropped, which is
precisely why the capture was worth running.

The route that works is capture-internal: join NEW FACT to the
`extract_edges.edge` **completion** that emitted it, which is itself attributed by
episode content. That reaches **2,173 (93.5%)**.

| prompt (cheap tier) | in scope | attributed | **rate** | dropped |
|---|---:|---:|---:|---|
| `extract_nodes.extract_text` | 613 | 613 | **100.0%** | 0 |
| `extract_edges.edge` | 613 | 613 | **100.0%** | 0 |
| `extract_nodes.extract_summaries_batch` | 242 | 242 | **100.0%** | 0 |
| `dedupe_nodes.nodes` | 487 | 487 | **100.0%** | 0 |
| `dedupe_edges.resolve_edge` | 2,324 | 2,173 | **93.5%** | 151 |
| **total** | **4,279** | **4,128** | **96.5%** | **151** |

**The 151 drops are all one cause: the same NEW FACT string was emitted from
episodes in more than one article.** They are dropped, not assigned. The obvious
tie-breaker — pick the nearest call in time — was checked and rejected: ingest runs
articles concurrently, and sorting the 1,834 episode-attributable calls by timestamp
gives **1,500 contiguous same-article runs over 83 articles** — ~18 context switches
per article, i.e. almost no temporal locality at all. "Nearest in time" would be a
guess dressed as a measurement, and an unattributed record on the wrong side of the
split is exactly the leakage the article split exists to prevent.

Where one fact text maps to several episodes of the **same** article the record is
kept with `episode_uuid: null` and the article set — enough for an article-level
split, which is all the split needs.

### Problem 2 — the rejection rates, which are a finding in their own right

Every captured completion is validated before it may become a target: it must have a
terminal `finish_reason`, parse, validate against its `RESPONSE_MODELS` entry, and
pass the semantic checks a JSON schema cannot express.

> **Superseded policy, kept because the numbers below are still the measurement.**
> This section originally continued: *"Nothing is repaired — a repaired target is
> neither what the model emitted nor a verified correct answer."* **That was too
> broad and has been overridden** (§2d). It holds only where repair requires
> judgement. Where the correct answer is *derivable*, a repaired target IS a
> verified correct answer. The table below is the **defect** table — it measures the
> cheap tier's real error rate, which is what it was always for — and §2d says what
> now happens to each row. Reproduce this exact table with `--no-repair`.

| prompt (cheap tier) | checked | rejected | **rate** | exposed | dominant defect |
|---|---:|---:|---:|---:|---|
| `extract_nodes.extract_summaries_batch` | 242 | 213 | **88.0%** | 242 | summary over 1,000 chars |
| `extract_edges.edge` | 613 | 126 | **20.6%** | 613 | `episode_indices` out of range |
| `extract_nodes.extract_text` | 613 | 2 | **0.3%** | 613 | `episode_indices` out of range |
| `dedupe_edges.resolve_edge` | 2,173 | 0 | **0.0%** | 1,019 | — |
| `dedupe_nodes.nodes` | 487 | 0 | **0.0%** | 487 | — |
| **total** | **4,128** | **341** | **8.3%** | | |

**Zero** records failed on `finish_reason`, zero were unparseable JSON, and zero
failed pydantic validation. Every rejection is semantic. Four findings come out of
this, and three of them are new to the project.

**(a) The dedup index failure is gone — and this is a real 0, not an empty one.**
`contradiction_gate.py:24-27` records 267 observed out-of-range dedup indices from
this exact model. Across 2,173 attributed `resolve_edge` calls there are now **none**.
1,019 of those calls emitted at least one index (max index seen: 9), so the check
could have fired ~1,000 times and did not. The mechanism is visible in the prompts:
`parse_candidate_counts` recovers `(N, M)` and **M is 0 on every single call** —
`contradiction_gate` empties the invalidation list, so the prompt carries one index
range instead of two, and `contradiction_gate.py:24-27` records that *all 267
observed failures landed in the second one*. Removing the second range removed the failure.
This is the strongest confirmation the contradiction-gate suspension has produced.

**(b) The out-of-range index-array failure did not disappear — it moved to
`extract_edges.edge`, where nothing was counting it.** Of 4,409 edges the cheap tier
emitted, **788 (17.9%) carry an `episode_indices` value that does not exist**. Each
call passes exactly one episode (`IngestDriver` adds one per `add_episode`), so the
only legal value is `[0]`; graphiti only emits its "Episode Attribution" instruction
when `len(episodes) > 1` (`edge_operations.py:171-181`), and it never appears in a
single record of this capture. The shape of the failure is unmistakable:

```
episode_indices value                  count   (4,409 cheap-tier edges)
[0]                                     3621   correct
[0,1,2,...,24]                           358   the full ascending run, cut off by maxItems
[24]                                      67   the cap value alone
everything else (single non-zero, part-runs) 363
```

`[0,1,…,24]` is **exactly** the pathology `graphiti_client._bound_index_arrays:93-113`
documents — an ascending integer run under a JSON grammar, where the only legal
continuations are digits, `,` and `]`. That docstring already says it was "observed
twice: an `episode_indices` run past 2,900 that exhausted max_tokens and truncated
into invalid JSON, and dedup indices referring to candidates that never existed"
(`graphiti_client.py:101-103`). What is new is the **rate**, and that the mitigation
only reached half of it: `maxItems: 25` fixed the *syntactic* half (the run no longer
eats `max_tokens` and truncates into invalid JSON — 0 truncated replies in 4,743
captured calls), while the *semantic* half is untouched and running at 17.9%. It has
been invisible because
`edge_operations.py:293-297` silently filters out-of-range indices and falls back to
"all episodes", which with one episode is the right answer anyway — so the graph
looks healthy and the model is wrong 1 edge in 6. **The project memory "maxItems
fixes it" should be read as "maxItems fixes the truncation, not the indices."**
`extract_text` has the same failure at a far lower rate: 11 of 3,908 entities.

**(c) 5.7% of extracted edges name an endpoint that is not in the ENTITIES list.**
253 of 4,409, plus 35 self-edges. `edge_operations.py:218-239` drops both outright,
so these are facts the corpus simply lost. Observed endpoints include `ransomware`,
`Linux` and `Amazon Neptune` — plausible strings that were never offered.

> **Disposal changed 2026-09-17 (§2d).** Because graphiti rejects these edges anyway,
> omitting them IS the correct answer and is derivable from the prompt's own ENTITIES
> list. They are now removed edge-by-edge rather than taking the whole record down:
> 161 of the 288 omitted in place, the remaining 127 inside 11 records that repair
> emptied and that were dropped for a different reason.

**(d) The summary prompt's length constraint is essentially ignored.** The prompt
says "Each summary must be under 1000 characters" (`prompts/extract_nodes.py:519`,
`MAX_SUMMARY_CHARS = 1000`). Of 380 summaries the cheap tier produced, **263 (69.2%)
are over**, median **1,827** chars, p90 **5,167**, max **12,847** — up to 12.8× the
stated limit. 213 of 242 calls contain at least one. This has been invisible for the
same reason as (b): `node_operations.py:999` applies `truncate_at_sentence`
unconditionally, so `Entity.summary` in the graph is always ≤1,000 chars and looks
fine.

This is the one rejection that materially costs the dataset, so it is a flag rather
than a fixed policy — see §6a.

**(e) A smaller oddity worth recording: the same prompt does not always get the same
answer.** 52 prompt texts appear more than once in the capture (all `resolve_edge` —
the same NEW FACT arriving from two chunks against an identical candidate list; they
are minutes apart, so these are not tenacity retries). **21 of the 52 got different
completions for byte-identical input.** They are all schema-valid and all in range,
so none is rejected, and they survive into the dataset as mutually inconsistent
targets — 44-odd rows out of 3,904, which is not worth special handling, but it is a
floor on how well any model can fit this data and it is worth knowing it exists.

### What the capture bought that the graph could not

The graph-derived build's two acknowledged holes are closed:

| | graph-derived (2026-09-16) | captured (2026-09-17) |
|---|---|---|
| `dedupe_nodes` positives | **none, at all** | **346 of 487 calls (71.0%)** have ≥1 real `duplicate_candidate_id` |
| `resolve_edge` positives | 351 synthetic alias swaps | **992 of 2,324 calls (42.7%)** have ≥1 real `duplicate_facts` index |

## 2d. The repair policy — targets are the CORRECT answer, 2026-09-17

**The point of this fine-tune is to replace `solar-pro4`, not to clone it.** A
dataset whose targets are "whatever solar-pro4 emitted" has a ceiling of exactly
solar-pro4, including the 17.9% of edges it mis-attributes. So where the correct
answer is **derivable**, the target is now corrected; where it would have to be
**generated**, nothing is invented and the record is still dropped. That single line
is the whole policy, and everything below is either an application of it or a
measurement of what it bought.

Repair is **per item inside a completion, never per record.** The drop-only build
threw away an entire `extract_edges.edge` record — all its other correctly-extracted
edges included — because one edge named an entity that was not offered. That is why
`edge` lost 20.6% of its examples to fix what was, item for item, a 6.5% defect rate.

### What is repaired, and why each is derivable rather than judged

| defect | items | the correct answer, and why it is *derivable* |
|---|---:|---|
| `episode_indices` out of range | 788 | **`[0]`.** Exactly one episode is ever in scope, verified four ways (below), so index 0 is the only legal value — and it is the schema field's own default. |
| endpoint name not in ENTITIES | 253 | **omit that edge.** `extract_edges.py:146-147` tells the model such an edge "will be rejected", and `edge_operations.py:218-239` does reject it. The corpus lost the fact either way. |
| self-edge, source == target | 35 | **omit that edge.** Same rejection site (`:231-238`), same reasoning. |

**The single-episode claim, verified four ways** — because everything in row 1 rests
on it and "the model is wrong, trust me" is not a target:

1. `ingest_driver.py:188-196` calls `add_text_episode` once per chunk.
2. `graphiti.add_episode` (`graphiti.py:1099-1111`) constructs **one** `EpisodicNode`
   and passes it *singular* to `extract_nodes` and `_extract_and_resolve_edges`, both
   of which do `episodes = episode if isinstance(episode, list) else [episode]`. So
   `len(episodes) == 1` at every extraction call this corpus ever made.
3. graphiti emits its `**Episode Attribution**` instruction **only** when
   `len(episodes) > 1` (`edge_operations.py:170-181`, `node_operations.py:104-112`).
   It appears in **zero of the 4,743 captured prompts** — an empirical check over the
   whole capture, not an inference from the code.
4. `Edge.episode_indices` and `ExtractedEntity.episode_indices` both
   `default_factory=lambda: [0]`, and their field descriptions say *"When processing a
   single episode, this should be `[0]`."*

The provenance consequence was checked against the live graph and recorded in
`docs/proposals/2026-09-15-bulk-ingest-assessment.md` (addendum 2026-09-17): **0
unattributed facts, 4,822 episode references, 0 dangling.** Today every possible
`episode_indices` value converges on the same correct attribution because there is
only one episode to point at — which is exactly why the defect has been invisible,
and exactly why it must not be distilled: under `add_episode_bulk` the same answer
becomes silent provenance corruption.

### The one judgement call, made explicitly

Removing edges can empty a completion's `edges` list. 40 records hit this. **Whether
`[]` is the *correct* answer or merely an *empty* one depends on the prompt, and the
prompt settles it:**

- **29 of the 40 offered ≤ 1 distinct entity** (26 offered exactly one, 3 offered
  none). With fewer than two names, *no valid edge is expressible at all* — every
  candidate edge is necessarily a self-edge, which graphiti rejects. `{"edges": []}`
  is therefore the only correct answer, is derivable from the prompt alone, and is
  **kept**. It is logged as its own repair class, `all_edges_invalid`.
- **11 offered ≥ 2 entities.** A valid edge *was* expressible and the model failed to
  name one. The correct answer is a different, non-empty set of edges — that is
  generation, not derivation — so these are **dropped**. Teaching "emit nothing here"
  would install an under-extraction habit, which is the same class of mistake as
  teaching truncation (§6a).

A record whose `edges` was *already* empty is untouched: that is an observed
negative, not a manufactured one.

### What is NOT repaired

`extract_nodes.extract_summaries_batch` — 213 of 242 calls contain a summary over
`MAX_SUMMARY_CHARS`. **The correct answer is a shorter summary, which cannot be
derived, only generated.** `truncate_at_sentence` is what graphiti applies
downstream, but truncation as a *training target* teaches the model to write long and
then stop abruptly — a different defect, not a fix. Left exactly as it was: 29 usable
records. §6a puts the options to you, costed.

Also unrepaired by design: `truncated_or_nonterminal`, `unparseable_json`,
`schema_invalid` and `empty_fact` have no derivable correct answer either. None of
the first three occurs in this capture and `empty_fact` occurs zero times; the guards
exist so a future capture cannot slip past.

## 3. Fidelity: proved, not asserted

The dataset must match graphiti 0.30.1's templates exactly — a fine-tune trained on
a paraphrase is trained on the wrong task. Two defences:

**The builder does not contain any prompt text.** It imports
`graphiti_core.prompts.prompt_library` and calls the real functions. This matters
more than it looks: `prompt_library` wraps every version in a `VersionWrapper` that
appends `DO_NOT_ESCAPE_UNICODE` to system messages (`prompts/lib.py:69-77`). Calling
the module-level functions directly would silently lose that line.

It then replays the mutation `OpenAIGenericClient.generate_response` performs before
the request goes out:

1. `messages[0].content += get_extraction_language_instruction(group_id)`
   (`openai_generic_client.py:203`)
2. `_clean_input` on every message (`:149`) — invoked through a real client instance
   so it is graphiti's code, not a copy.

The cheap tier runs `cheap_llm_client_mode='generic_json_schema'`
(`config.py:236-237`), so the JSON schema travels in `response_format` and is **not**
injected into the prompt text — the `json_object` branch at `:193-200` does that, and
it is not the branch we use.

**Verification.** A harness drove graphiti's own call path — `extract_nodes`,
`extract_edges`, `_resolve_with_llm`, `_process_summary_flight`
(`graphiti_core.utils.maintenance.*`) — against a fake LLM transport that captures
what *would* have been sent, then compared it to the builder's output for the same
episode:

```
extract_nodes.extract_text:            MATCH
extract_edges.edge:                    MATCH
dedupe_nodes.nodes:                    MATCH
extract_nodes.extract_summaries_batch: MATCH
```

Byte-for-byte, including the unicode note, the multilingual suffix and `_clean_input`.
Two bugs were caught this way before review and fixed rather than shipped: `edge` was
passing `nodes` as a list of bare name strings where graphiti passes
`[{'name': ..., 'entity_types': ...}]` (`edge_operations.py:189`), and `reference_time`
was being rendered from Neo4j's nanosecond `toString()` instead of `str(datetime)`.
Neither would have raised an error — both would have silently trained the model on a
prompt shape it will never see. Four further defects came out of code review; see §2b.

All four comparisons were re-run after those fixes and still MATCH, and the datetime
conversion is now cross-checked against the driver's native path rather than itself.

(`extract_summaries_batch` is compared with the candidate summaries blanked, because
the builder deliberately sends an empty prior summary — the call-time state is
unrecoverable. That is the §2 fidelity gap, not a rendering mismatch.)

**A second, independent tripwire** for `resolve_edge`: all 1,156 rendered dedup
prompts were fed to this project's own `dedup_guard.parse_candidate_counts`
(`dedup_guard.py:106-122`), which is deliberately coupled to graphiti's prompt text.
All 1,156 parsed, every `N` matched the record's candidate count, and every `M` was
0 — confirming the single-index-range shape the contradiction gate produces (below).

**And the targets are schema-valid**: all 2,890 assistant messages parse into their
pydantic `response_model` (`ExtractedEntities`, `ExtractedEdges`,
`SummarizedEntities`, `EdgeDuplicate`, `NodeResolutions`). 0 failures.

`validate_capture` calls `parse_candidate_counts` on every captured `resolve_edge`
prompt to recover the index range, because the range is a property of the prompt and
no schema can express it. All 2,173 parsed. The fidelity argument also inverts for
the captured build — there is nothing to prove byte-exact, because nothing is
rendered. The prompts ARE the bytes that went on the wire, post-`_clean_input`,
post-multilingual-suffix, straight out of `instrument`'s wrapper at the transport
boundary.

`contradiction_gate` returns an empty `SearchResults()` for the unfiltered

## 4. Format

**Chat-completion style, JSONL, one record per line.**

Why chat and not completion-style: graphiti sends role-separated messages
(`openai_generic_client.py:150-155` builds `{'role': ..., 'content': ...}`), and
serving will be an OpenAI-compatible endpoint. A completion-style fine-tune would
have to invent a flattening that does not match what the serving stack sends, which
reintroduces exactly the train/serve mismatch this whole exercise is trying to avoid.

```jsonc
{
  "prompt_name": "dedupe_edges.resolve_edge",
  "response_schema": "EdgeDuplicate",          // key into schemas.json
  "messages": [
    {"role": "system",    "content": "..."},   // verbatim, post-mutation
    {"role": "user",      "content": "..."},
    {"role": "assistant", "content": "{\"duplicate_facts\": [], \"contradicted_facts\": []}"}
  ],
  "meta": {
    "provenance": "graph_derived_negative",    // see below
    "fidelity": ["true negative: this fact survived as its own edge, ...", "..."],
    "loss_weight": 2.21,                       // see §6
    "episode_uuid": "...", "article_id": "...", "chunk_index": 3,
    "fact_uuid": "...", "n_candidates": 7
  }
}
```

`provenance` is one of:

| value | meaning |
|---|---|
| `captured` | **the string the model actually emitted for this exact prompt.** The strongest provenance in the dataset, and the only one `data/ft-captured/` contains |
| `graph_derived` | the target is what the pipeline produced, with `fidelity` caveats |
| `graph_derived_negative` | a real negative — the call happened and "no duplicate" was correct |
| `synthetic_alias_positive` | **REMOVED from the shipped dataset.** See §7 |

A `captured` record carries six extra `meta` fields so the chain back to the
capture file stays auditable per example:

```jsonc
"meta": {
  "provenance": "captured",
  "attribution_route": "episode_content",   // or new_fact_via_capture / new_fact_via_graph
  "capture_call_id": "…",                   // the exact line in the capture JSONL
  "capture_tier": "cheap",
  "capture_model": "upstage/solar-pro4",
  "capture_finish_reason": "stop",
  "target_normalised": true,                // see below
  "repaired": [],                           // §2d -- ALWAYS present, [] when untouched
  "loss_weight": 1.26, "loss_basis": "full",
  "episode_uuid": "…", "article_id": "…", "chunk_index": 3
}
```

**`repaired`** (added 2026-09-17) is one entry per corrected item —
`{defect, item, action}` — and is present on every captured record, `[]` when the
target is exactly what the model emitted. Provenance stays `captured` because the
*prompt* is untouched wire traffic either way; when `repaired` is non-empty,
`fidelity[1]` is replaced by a `TARGET CORRECTED:` note. See §2d.

**`target_normalised`.** By default the target is the compact JSON serialisation of
the *validated* `response_model` instance rather than the completion's raw bytes.
This changes **no field value** — only whitespace, key order, and pydantic defaults
materialised for fields the reply omitted — and it is exactly the object graphiti
itself consumes (`ExtractedEdges(**llm_response)`). The reason is measurable:
solar-pro4 emits both pretty-printed and compact JSON for the same prompt type
(`resolve_edge` 2,118 pretty / 206 compact; `dedupe_nodes` 39 pretty / 448 compact),
and training on that mix spends capacity on a variable that the serving stack's
`json.loads` discards. `--raw-targets` keeps the bytes verbatim if you would rather
have byte-level fidelity than formatting consistency.

`schemas.json` carries the exact `response_format` payload per prompt, including the
`maxItems: 25` that `graphiti_client._bound_index_arrays` injects (`:116-126`, bound
from `config.py:75`). Emitting it separately keeps the JSONL readable and gives the
training/serving stack the grammar directly.

> `graphiti_client._bound_index_arrays:96-98` states *"graphiti emits three such
> fields"* and lists `ExtractedEdges.Edge.episode_indices`,
> `EdgeDuplicate.duplicate_facts`, `EdgeDuplicate.contradicted_facts`. Enumerating
> the five response models' JSON schemas finds **four**: it misses
> `ExtractedEntities.ExtractedEntity.episode_indices`

## 5. The schema problem

Every recorded cheap-tier failure in this project has been a **format** failure:

- *graphiti unbounded index arrays — the real cause of every cheap-model extraction
  failure; `maxItems` fixes it, repetition penalties make it worse*
- *ling is dead; require `structured_outputs` in `supported_parameters` and probe
  with a strict `json_schema` before trusting any cheap model*

`graphiti_client._bound_index_arrays:93-113` documents the mechanism precisely: an
ascending integer run is the strongest sequence prior there is, and under a JSON
grammar the only legal continuations are digits, `,` and `]`, so a weak model counts
until `max_tokens` runs out and truncates into invalid JSON. Observed with an
`episode_indices` run past 2,900.

> **Correction from the capture, 2026-09-17 — `maxItems` fixed the truncation, not
> the indices.** In 4,409 cheap-tier edges the run still happens: `[0,1,…,24]`
> appears **358 times** and stops at 24 because that is where `maxItems: 25` cuts it
> off. Another 67 edges answer `[24]` — the cap value alone. 788 edges (17.9%) carry
> an `episode_indices` value that does not exist, where the only legal value is `[0]`.
> So the format failure became a *semantic* failure of the same shape, and it is
> invisible because `edge_operations.py:293-297` filters the bad indices and falls
> back to "all episodes", which with one episode is the right answer anyway. The
> project memory "`maxItems` fixes it" needs the qualifier: it fixes the truncation
> into invalid JSON. **This is the single strongest argument in the document for
> fine-tuning at all** — it is precisely the class a grammar cannot reach (below).

### Does grammar-constrained decoding make the dataset moot?

**Partly — and knowing exactly which part is the useful answer.**

A hard grammar (vLLM + xgrammar/outlines) makes *syntactic* malformation
**unrepresentable**: the reply is always parseable JSON matching the schema, arrays
respect `maxItems`, enum fields respect their enums. That class of failure — the one
that killed ling and forced the frequency-penalty and `maxItems` patches — is solved
by the serving stack, not by the fine-tune. It is strictly stronger than any API's
best-effort structured-output mode, and graphiti deliberately omits `strict: true`
(`openai_generic_client.py:112-117`), so today enforcement is provider-dependent.

What a grammar **cannot** fix, and what this dataset therefore has to teach:

1. **Semantic validity inside a syntactically legal shape.** A grammar will happily
   emit `duplicate_facts: [17]` when only indices 0-6 exist. That was the observed
   failure — 267 out-of-range indices, now zero on the dedup call since the
   contradiction gate collapsed the prompt to one range (§3), but running at **17.9%
   on `extract_edges.edge`'s `episode_indices`**, where nothing counts it — and
   `dedup_guard` refuses to clamp
   it on purpose (`:32-36`): under constrained decoding a `maximum` bound would turn
   `[10, 11]` into an in-range `[1, 1]`, "a wrong dedup that merges two distinct
   facts and is invisible afterwards. A detectable drop is strictly better than an
   undetectable merge." **The index range is a property of the prompt, not of the
   schema, so only training can teach it.**
2. **`source_entity_name` / `target_entity_name` must be drawn from the ENTITIES
   list** (`extract_edges.py:146-147`: "Using names not in the list will cause the
   edge to be rejected"). A grammar cannot express "one of the strings that appeared
   earlier in this prompt" — a dynamic per-request enum would, but graphiti builds
   the schema from a static pydantic model.
3. **Calibration** — how many facts a chunk should yield, when to answer `-1`, when
   an empty list is right. `CHEAP_TIER_SALIENCE` (`ontology.py`) exists purely
   because the cheap model over-enumerated dense tables; that is a learned
   behaviour, not a grammar.

**So: use grammar-constrained decoding *and* fine-tune, and understand the division
of labour.** The grammar buys syntax for free, which means the fine-tune's job is
narrower than the proposal assumed — it is a *pointing* task (pick the right index,
pick names that exist, decide how much to emit), not a JSON-formatting task. That is
good news for a 4B (§8).

**How the dataset teaches the schema anyway:** every target is emitted as the exact
compact JSON serialisation of a validated `response_model` instance, so the model
sees the canonical key order, the `null` convention for absent timestamps, and the
`[0]` convention for `episode_indices` in every single example. On the captured
build that last point is earned rather than assumed, and since 2026-09-17 it is
earned *without paying for it*: the 788 out-of-range `episode_indices` are now
**repaired to `[0]`** rather than taken down with the 126 records that carried them
(§2d), so every surviving example shows the correct `[0]` **and** 115 of those
records' other, correct work survives too. 4,128/4,128 attributed completions parsed
and validated against their pydantic model with zero failures, and the written files
re-validate at **0 residual defects** over all 12,605 rows.

## 6. Weighting — TARGET_MIX, the full-token basis, and `--upsample`

The fine-tune replaces `solar-pro4` **completely**, all five prompts, so the mix
tracks the measured LLM-time share rather than hedging toward the calls a 4B is most
likely to get right. `TARGET_MIX` as committed:

| prompt | LLM-time share (2026-09-14 A/B) | `TARGET_MIX` |
|---|---:|---:|
| `extract_edges.edge` | 33.6% | **0.34** |
| `dedupe_edges.resolve_edge` | 22.9% | **0.25** |
| `extract_nodes.extract_summaries_batch` | 19.8% | **0.18** |
| `extract_nodes.extract_text` | 12.7% | **0.13** |
| `dedupe_nodes.nodes` | 10.9% | **0.10** |

`resolve_edge` keeps a small boost above its 22.9% time share because every recorded

under-weighting it would optimise hardest for the part we were always going to get.

### The finding: example share is not gradient share

A prompt's influence on the gradient is its share of **tokens that carry loss**, and
which tokens those are depends on the masking regime — which is why `meta.loss_basis`
is written on every record. Completion-masked SFT backprops only through the last
message; training on **full sequences** (no completion-only mask, which is what this
fine-tune does) backprops through everything. On this dataset the three views
diverge enormously. Measured on the 3,904 captured, repaired examples:

| prompt | by example count | **by full tokens** | by completion tokens |
|---|---:|---:|---:|
| `extract_edges.edge` | 15.4% | **38.1%** | 68.6% |
| `dedupe_edges.resolve_edge` | 55.7% | **14.5%** | 5.9% |
| `extract_nodes.extract_summaries_batch` | 0.7% | **1.2%** | 1.6% |
| `extract_nodes.extract_text` | 15.7% | **17.5%** | 17.1% |
| `dedupe_nodes.nodes` | 12.5% | **28.7%** | 7.0% |

*(Measured on the 3,904 repaired examples. The drop-only build's figures were
12.9/33.2/62.9, 57.4/15.6/6.9, 0.8/1.3/1.8, 16.1/18.9/20.1, 12.9/31.0/8.2 — repair
adds 115 `edge` records, which is why `edge` rises and everything else is diluted.)*

A `resolve_edge` target is ~12 tokens; an `edge` target is ~426 and a
`dedupe_nodes` prompt is ~6,700. So a dataset that is 57.4% `resolve_edge` *by
example count* is 15.6% of it by full tokens — and would be 6.9% under a completion
mask. Building the file to the nominal mix and training normally produces close to
the opposite of the intended fine-tune, whichever regime you are in.

**Two levers, and the file is self-describing about which it assumes:**

1. `meta.loss_weight` — set so `TARGET_MIX` is the token share under
   `--loss-basis` (default `full`, matching this fine-tune). Weights on the shipped
   build: `summaries_batch` 10.96, `resolve_edge` 1.26, `edge` 0.65, `text` 0.54,
   `dedupe_nodes` 0.25. Mean is normalised to 1.0 so the effective learning rate is
   comparable to an unweighted run. Note how much narrower this spread is than the
   ~100× the completion basis produced — **that is the basis doing its job**, not a
   different dataset.
2. `--upsample` — for TRL's `SFTTrainer` (which Unsloth wraps) and anything else
   that cannot read per-example weights. **It repeats by the RAW `target/actual`
   token ratio, never by `round(loss_weight)`:** `loss_weight` is mean-normalised
   and therefore *relative*, where a repeat count must be *absolute*. Using the
   weight directly landed `resolve_edge` at 11.7% of tokens against a 25% target —
   under half — while printing a report that looked reasonable. TRAIN split only;
   repeating validation examples would weight the val loss toward the repeated
   prompts, and a repeat crossing the boundary would be leakage. Every copy carries
   a distinct `meta.repeat_index` so a dedupe step downstream cannot collapse them.

### Does `--upsample` still hit the target? Yes — where the data allows

| prompt | train before | after | tokens% | target% | gap |
|---|---:|---:|---:|---:|---:|
| `extract_edges.edge` | 484 | 1,452 | 43.6% | 34.0% | +9.6 |
| `dedupe_edges.resolve_edge` | 1,758 | 8,790 | 27.9% | 25.0% | +2.9 |
| `extract_nodes.extract_text` | 492 | 984 | 13.5% | 13.0% | +0.5 |
| `dedupe_nodes.nodes` | 387 | 387 | 10.8% | 10.0% | +0.8 |
| `extract_nodes.extract_summaries_batch` | 19 | 228 | 4.2% | 18.0% | **−13.8** |

**The one large gap has a single cause, and it is not the upsampler.** Rejecting
88% of the summary calls (§2c(d)) leaves 19 distinct train examples; at
`--max-repeat 12` they reach 228 copies and 4.2% of tokens. The missing 13.8 points
redistribute over the other four, which is the whole of their overshoot. Repetition
can only *add* tokens, so a prompt already over its target cannot be brought down
this way (`upsample_train` says so and `_print_upsample_report` shows the residual
rather than hiding it).

Proof that the upsampler itself is intact: the drop-only build with
`--allow-overlong-summaries` — identical code path, 213 more summary records — lands
**every prompt within 1.4 points of target**: edge 32.9/34.0, resolve_edge
26.4/25.0, summaries 17.8/18.0, text 12.7/13.0, dedupe_nodes 10.2/10.0. *(Those five
figures are from the drop-only build and have not been re-measured against the
repaired one; the conclusion they support — that the gap is the summary split, not
the upsampler — is unaffected.)*

**`edge`'s overshoot grew from +4.2 to +9.6, and that is repair working, not
failing.** Repair returned 115 `edge` records, so the prompt with the largest target
share got 23.6% more data while the four prompts it competes with got almost none.
Repetition can only add tokens, so an already-over prompt cannot be pulled down —
only discarding examples would do it, and discarding `edge` examples is the last
thing this dataset should do (§6, §10). `meta.loss_weight` handles it exactly for any
trainer that reads per-example weights: `edge` drops to **0.65**.

### 6a. The summary split: the options, costed — and a measurement that narrows them

This is the one decision the rebuild cannot make for you. **It is also the one place
the repair policy deliberately stops** (§2d): the correct answer is a *shorter
summary*, which can be generated but not derived, so the builder will not invent one.

**A new measurement changes what the options are worth.** The capture already
contains **20 `extract_summaries_batch` calls answered by `gpt-5-mini`** — the strong
tier, on the 6 strong-tier articles. They cost nothing to analyse, and this prompt is
the one prompt in the set that is **tier-identical**: `extract_summaries_batch` does
not interpolate `custom_extraction_instructions` at all
(`prompts/extract_nodes.py:509-525`, unlike `:205`, `:258`, `:327`), so
`CHEAP_TIER_SALIENCE` never enters it and the train/serve mismatch that rules the
strong tier out elsewhere (§2c) **does not apply here.** They are directly comparable:

| tier | model | calls | summaries | over 1,000 chars | calls w/ ≥1 over | median | max |
|---|---|---:|---:|---:|---:|---:|---:|
| cheap | `upstage/solar-pro4` | 242 | 380 | **263 (69.2%)** | **213 (88.0%)** | 1,824 | 12,847 |
| strong | `gpt-5-mini` | 20 | 34 | **18 (52.9%)** | **16 (80.0%)** | 1,088 | 1,762 |

**`gpt-5-mini` also breaks the constraint — on more than half its summaries.** It is
far better behaved in the tail (max 1,762 against 12,847, i.e. 1.8× over rather than
12.8×), but it is not a compliant teacher, and a regenerated dataset would fail the
very check that rejected the cheap tier's. n is small (20 calls), so treat this as
strong indicative evidence rather than a settled rate — but it is a measurement of
the exact model, on the exact prompt, and it is free.

**The options:**

- **(a) Ship as built (default, and my recommendation).** 29 usable records, 19
  distinct in train, 13.8 points under target. Honest; the fine-tune under-learns
  this prompt. **Cost: $0.** Pairs naturally with (d).
- **(b) `--allow-overlong-summaries`.** ~4,000 usable examples, mix within 1.4
  points — and you distil a model that exceeds an explicit prompt constraint on 69%
  of its summaries, by a median of 1.8× and a max of 12.8×. graphiti truncates the
  result exactly as it truncates solar-pro4's, so the *graph* stays fine; the *model*
  learns to overrun. **Cost: $0.**
- **(b′) Truncate the targets with `truncate_at_sentence`.** **Not offered, and not
  recommended.** It is what graphiti applies downstream, so it would look principled —
  but as a *training target* it teaches "write long, then stop abruptly", which is a
  different defect substituted for the original, not a fix. This is the boundary of
  the repair policy, not an oversight.
- **(c) Regenerate the 213 defective calls with `gpt-5-mini`. COSTS MONEY — NOT DONE,
  NOT AUTHORISED.** Cheaper and far safer than §2's Option C sounded, because the
  prompts are already captured verbatim: this is an **offline replay of 213 stored
  prompts**, not a re-ingest. No graph write, no ingest path, no risk to the 999-entity
  baseline.
  - **Measured basis (not an estimate):** those 213 calls carry **1,102,932 prompt
    tokens**; solar-pro4 spent **171,346 completion tokens** on them, and a compliant
    reply would be lower (~1.8 summaries/call × ≤250 tok ≈ **95 k**).
  - **Dollar figure [estimate] — the token counts are measured, the RATE is the
    guess.** The repo has no price table (§2, Option C), so at the $0.25–$2.00 per 1 M
    input / $1–$8 per 1 M output band small strong-tier API models occupy, 1.1 M in +
    ~0.1 M out is roughly **$1–$3**. Treat the band, not the midpoint, as the claim.
    A priced probe on ~2 calls would replace this with a real number for a few cents,
    per the standing cost rule in CLAUDE.md.
  - **The catch is the measurement above, not the price.** 52.9% of `gpt-5-mini`'s
    summaries on this prompt are already over the limit, so plain regeneration buys
    targets that still fail validation. **Do not authorise (c) on its own.**
- **(d) Take `extract_nodes.extract_summaries_batch` out of scope** and leave it on
  the API model. §10 already proposes gating prompts separately, `DedupIndexStats`
  and fact yield are reported independently, and this is the prompt with both the
  weakest data and the least leverage (19.8% of LLM time, no index-picking, no
  provenance consequence). **Cost: $0.** This was the 2026-09-16 recommendation and
  it survives the new measurement intact.
- **(e) If the prompt must be in scope: generate-and-check, not generate.** The only
  route to *verified correct* targets. Replay the 213 prompts against `gpt-5-mini`
  and **reject-and-retry any reply containing a summary over 1,000 chars**, keeping
  only compliant replies. That converts generation into something the validator can
  certify, which is the same standard the derivable repairs meet. **Cost [estimate]:
  (c)'s $1–$3 × a retry factor of ~2–3 given the 52.9% per-summary violation rate,
  so ~$3–$9**, plus a small runner. **Also costs money and is NOT authorised — and if
  anything here is to be authorised, it should be this rather than (c).**

**Recommendation: (a) + (d)** — ship the 29 honest records and gate this prompt
separately, leaving it on the API model. Reconsider only if an A/B shows summary
quality is actually binding on answer quality, and if so authorise **(e)**, not (c).

### (historical — the graph-derived build)

`resolve_edge` negatives are faithful. Positives are not derivable (§2). A
negatives-only split would teach the model to **always answer `[]`**, which is worse
than no fine-tune at all — the dedup call would become a no-op and duplicate facts
would enter the graph permanently (`dedup_guard.py:11-13`).

The builder therefore derives 351 `synthetic_alias_positive` records (175 survive
the mix into the current build — 15% of the `resolve_edge` split). The rule is
narrow and auditable: take a real fact, swap a canonical term for a non-canonical

to fold into that canonical name (`Kubernetes`↔`K8s`, `Amazon S3`↔`S3 buckets`,

declared semantics**, and it is not a verbatim string match, so graphiti's exact-match
fast path (`edge_operations.py`, `_normalize_string_exact`) would not have
intercepted it. The rule used is written into each record's `meta.fidelity`.

**They are still synthetic. No model emitted them.** Review the sample before
training, and prefer replacing them wholesale with Option B's captured positives.
`--no-synthetic-positives` omits them.

`dedupe_nodes.nodes` has **no** positives, synthetic or otherwise, and the builder
says so in every record. This is the largest remaining hole in the dataset.

## 8. Train/validation split, and the gate

**Split by article, not by episode.** Episodes of one article share entities and
near-identical prose; an episode-level split leaks the answer across the boundary.
`split_of` hashes `article_id` (SHA-256, first 8 hex) into a stable 80/20 split.

Verified on the shipped captured build, **re-verified after repair**: **60 train
articles / 17 val articles, 0 article overlap, and 0 `capture_call_id` overlap** (the
second check matters because `--upsample` duplicates rows — it confirms no repeat
crossed the boundary). 60 + 17 = 77, which is exactly the number of articles the
cheap tier processed: the other 6 of the 83 were routed entirely to the strong tier
and are excluded by `--capture-tier cheap` (§2c). Nothing is silently missing.

Repair returns 117 records to the pool but **cannot move the boundary**: `split_of`
hashes the `article_id`, which repair never touches, so a repaired record lands on
exactly the side its article was already on. Both overlap checks were re-run against
the written `train.jsonl` / `val.jsonl` after the repaired build and are still 0.

**This is the constraint that forced the attribution work in §2c.** A captured
record carries no `article_id`; without recovering one, the only options are an
episode-level or random split, both of which leak. The 151 `resolve_edge` records
whose NEW FACT spans articles are dropped for the same reason — placing them on
either side would defeat the split they cannot be assigned to.

**What the validation set is for — and what it is not.** Held-out cross-entropy tells
you the model learned this dataset's idiosyncrasies, including the ones §2 says are
wrong (post-dedup names, final-state summaries). It is a training-health signal only.
**It must not be the acceptance gate.**

**The acceptance gate is the measurement that already exists.** Do not invent a
metric. Run `.superpowers/sdd/ab-w8-validation.py` — the same 83 pilot articles, the
cheap tier swapped to the fine-tune, against the 999-entity sequential baseline. It
already reports every number that matters:

| signal | baseline | source |
|---|---|---|
| entity count after merge | **999**, 0 exact-name duplicates | `ab-w8-validation.py:5, 39` |
| near-duplicate groups | 6 | `:172` |
| out-of-range dedup indices | `DedupIndexStats.summary()` — `invalid_calls`, `dup_in_invalidation_range`, `dup_beyond_range` | `:177`, `dedup_guard.py:56-81` |
| fact yield | 3,590 `RELATES_TO` | live graph |
| provenance integrity | `eval.provenance_report` | `eval.py:183` |
| noise rate | `eval.noise_report` (pure Cypher, free) | `eval.py:65` |
| **out-of-range `episode_indices` on `extract_edges.edge`** | **17.9% of 4,409 emitted edges** — measured 2026-09-17 from the capture, not currently counted in production (§13) | §2c(b) |
| **summaries over `MAX_SUMMARY_CHARS`** | **69.2% of 380** — same caveat. `gpt-5-mini` is at **52.9% of 34** on the same prompt, so this is not a cheap-tier-only defect | §2c(d), §6a |
| fact / type quality | `eval.fact_quality`, `eval.type_precision` (**LLM judge — costs money**) | `eval.py:297`, `:390` |

`DedupIndexStats` was described here as "the single most direct read on whether the
fine-tune worked". **The capture changed that, and the change is worth stating
plainly: the baseline it would be measured against is now zero** (§2c(a)), so it can
no longer show an improvement — only a regression. That is still worth having as a
tripwire, but it is no longer the headline signal.

The headline signal moved to the two rows added above. `episode_indices` on
`extract_edges.edge` is out of range on 17.9% of emitted edges at baseline, and the
dataset now **repairs** every one of them to `[0]` rather than dropping the record
that carried it (§2d), so the fine-tune's targets are 100% correct on it — over
**602** `edge` examples instead of 487. That strengthens this gate rather than
changing it: the targets were already 100% correct under drop-only, but they taught
`[0]` from 23.6% less data, and the 115 rescued records are precisely the ones where
the model got the indices wrong, i.e. the examples that carry the correction signal.
Neither number is counted in production today (§13), which is the first thing to fix
before an A/B — a gate you cannot read is not a gate. A fine-tune that does not beat
17.9% has not earned its place, whatever its validation loss says.

**Method constraint:** the A/B must use supersede-and-restore (`ab-revert.py`),
never a reset of the semantic layer. The 999-entity graph is the only reference copy
and destroying it destroys the baseline.

**Cost note:** running the A/B is not free even with a local model — the strong tier
still handles dense-matrix articles and the embedder still runs. Budget it as a
paid run and authorise it explicitly.

## 9. The coupling risk, stated plainly

**A fine-tune trained on graphiti 0.30.1's prompts goes stale the moment graphiti is
upgraded.** This project pins `graphiti-core==0.30.1` and never forks it, extending
instead by patching imported-by-name references (`dedup_guard`,
`contradiction_gate`, `deterministic_valid_at`, `lean_edge_search`). A fine-tune adds
a **second artefact that must move in lockstep with a library we do not control** —
and unlike the patches, it cannot be fixed by editing a file. It has to be retrained.

This is the 2026-09-15 proposal's central argument against fine-tuning, and building
the dataset does not refute it. What the dataset does change is the *cost* of the
coupling:

- The builder contains **no prompt text**. It imports `prompt_library` and renders
  whatever the installed graphiti says. On a graphiti upgrade, re-running it
  regenerates a correct dataset with no authoring work.
- The **targets survive an upgrade**; only the prompt rendering changes. Entity,
  fact and dedup-decision labels are properties of the corpus, not of the template.
- So the maintenance unit is **"re-render and retrain" (~free + GPU hours)**, not
  "re-label" (~$10 + a day).

**Concretely, what to commit to:**

1. Pin `graphiti-core==0.30.1` *harder* — it is now load-bearing for a model
   artefact, not just for code.
2. Add a **tripwire test** that fails CI when any of the five prompt templates
   changes. `tests/unit/test_contradiction_gate.py` already establishes the
   call-site-tripwire pattern, and `dedup_guard.parse_candidate_counts` is already
   coupled-and-tested this way. Hash the rendered output of each of the five prompt
   functions against a fixed context; a graphiti bump that changes one turns red.
   Without this the staleness is **silent** — the model keeps answering, just worse.
3. Treat the model version and the graphiti version as **one unit** in deployment.

**And the honest framing:** if the goal is genuinely "settle on one extraction model
and stop changing it", the proposal is right that self-hosted base weights behind a
hard grammar is the lower-coupling answer, and should be measured *first*. This
dataset's real value is that it is now **free to produce and free to regenerate**, so
the fine-tune can be tried as step 4 without a labelling project in front of it —
which is precisely the position the proposal wrongly believed it was already in.

## 10. 4B versus the 9B the proposal assessed

The proposal evaluated a 9B and explicitly declined to claim anything about its
quality ("No claim is made here about Qwen-3.5-9B's specific quality on this task").
A 4B is less than half the parameters. What changes:

**Gets easier / stays fine**

- **Hardware stops being the gate.** The proposal's blocker was "`nvidia-smi` finds
  no GPU" and "a 9B wants ~24 GB at bf16, ~16 GB quantized". A 4B is ~8-9 GB at
  bf16 and ~4-5 GB at 4-bit — it fits on a single consumer card, and LoRA fine-tuning
  fits comfortably on 24 GB. **[estimate]**, standard parameter arithmetic, not
  measured here. This may convert "collapses entirely" into "feasible on one
  workstation".
- **Format conformance is not a size problem** once grammar-constrained decoding is
  on (§5). The failures that killed ling were decoding-dynamics failures, and a
  grammar fixes those for a 4B exactly as well as for a 9B.
- **Index-picking is the best-suited 35% of the workload.** `resolve_edge` is
  near-classification over a short prompt (median **739** captured tokens) with a
  ~12-token answer, and the captured data says the teacher is already perfect at it
  (§2c(a)) — which makes it the cheapest part to match and the least likely to
  regress. `dedupe_nodes` is not short: its median prompt is **6,693** tokens, so
  "index-picking is easy because the prompts are small" is only true of one of the
  two.

**Gets harder**

- **`extract_edges.edge` is the real risk.** 33.6% of LLM time, a ~7.5 k-token
  prompt, a ~460-token structured answer, and an instruction set that is genuinely
  long — `EXTRACTION_INSTRUCTIONS` + `CHEAP_TIER_SALIENCE` (`ontology.py`) run to
  several hundred words of type boundaries and canonical-name rules, on top of
  graphiti's own seven extraction rules. Following many simultaneous negative
  constraints ("never generalize", "never the same entity twice", "only names from
  the list") is where parameter count tells. **Fine-tuning helps here more than
  anywhere else**, because the instructions can be partly absorbed into weights —
  but a 4B is more likely to need the fine-tune to *reach* baseline rather than to
  beat it.
- **Long-context degradation.** p95 prompt is 8.2 k tokens and the max is **19.9 k**
  on the captured build (10.3 k / 17.3 k on the graph-derived one).
  Small models degrade faster over long contexts, and the `previous_episodes` block
  is a large, low-value part of that (10 prior episodes, often unrelated). If the
  4B struggles, **dropping `previous_episodes` is the first lever** — it is a
  graphiti default, not a project requirement, and `add_episode` accepts
  `previous_episode_uuids` to override it (`graphiti.py:992`).
- **Over-enumeration risk returns.** `CHEAP_TIER_SALIENCE` exists because the
  previous cheap model produced one fact per table cell. A smaller model is *more*
  prone to that, and `maxItems` bounds the index arrays but not the `edges` list
  (deliberately — `_bound_index_arrays:106-108` leaves arrays of objects alone so
  fact yield is untouched).

**Practical consequence:** consider training **two adapters or a mixed adapter with
an explicit prompt-type signal**, and gate them separately. Index-picking is likely
to pass at 4B; `extract_edges.edge` may not. Measuring them separately is cheap —
`DedupIndexStats` and fact yield are already reported independently by the A/B
runner — and it avoids discarding a fine-tune that succeeded at 40% of the workload
because it failed at another 34%. It also preserves the option of keeping
`gpt-5-mini` on edge extraction while a local 4B takes the dedup calls.

Capture-path flags: **`--no-repair`** (§2d — drop every defective record instead of
correcting the derivable ones; the old behaviour, kept so the two can be compared),
`--capture-tier {cheap,strong,both}` (default `cheap`, §2c),

records, which are always serialised from the corrected object), `--mix`
(down-sample to `TARGET_MIX` by example count — on by default for the graph build,
off for the capture build, because captured pairs are scarce and `--upsample` reaches
the same token target without discarding any). Shared flags: `--prompts` (subset),
`--loss-basis {full,completion}`, `--upsample` / `--max-repeat`, `--val-fraction`,
`--seed`. Graph-path only: `--tier strong`, `--no-synthetic-positives`.

**The committed sample deliberately over-represents repaired records.** Repaired
records are ~3% of the build, so a uniform draw of 20 would show none, and the sample
exists so the repair policy can be inspected per example rather than taken on trust.
`--sample-only` mixes to a pool 20× the sample size and then reserves up to 6 slots
for repaired records, spread across the defect classes — the shipped sample shows 6,
covering all four (`episode_index_out_of_range`, `entity_name_not_in_list`,
`self_edge`, `all_edges_invalid`). The digest header says so in bold. **Do not read a
repair rate off `sample.jsonl`;** the rates are in §2d and in the build report.

## 13. Follow-ups this rebuild opened (not done here — no `src/` changes)

1. **`episode_indices` on `extract_edges.edge` is wrong 17.9% of the time and
   nothing counts it.** `dedup_guard` counts out-of-range indices on the *dedup*
   call only. The same failure class on the extraction call is invisible because
   `edge_operations.py:293-297` filters silently. A counter in the same shape as
   `DedupIndexStats` would make it visible in production, and it is a candidate A/B
   signal in its own right (§8's gate table). **Now the more urgent of the two:**
   §2d makes this the defect the dataset most directly teaches against, and §8's
   gate cannot read it. `repair_capture`'s predicate is the counter, already
   written — `_bad_indices` plus `_n_episodes_in_prompt` is the whole of it.
2. **Summaries exceed `MAX_SUMMARY_CHARS` 69% of the time** and
   `truncate_at_sentence` hides it. Worth a log line at minimum — a summary truncated
   from 12,847 chars is not "a summary", it is a first paragraph.
   **Sharpened 2026-09-17: this is not a cheap-tier problem.** `gpt-5-mini` is over
   the limit on **52.9%** of its summaries on the same prompt (§6a). When both tiers
   ignore an instruction, the instruction is the suspect, and two concrete things are
   wrong with this one — both verified in graphiti 0.30.1, both free to change:
   - The constraint lives **only in prose** (`prompts/extract_nodes.py:519`, "Each
     summary must be under 1000 characters"). The pydantic field the model is
     actually filling is `SummarizedEntity.summary`, described as merely
     `'Updated summary for the entity'` (`:49-50`) — the schema, which is the part a
     structured-output model attends to most reliably, says nothing about length.
   - **A character count is a bad instruction for a token predictor.** graphiti's own
     `extract_summary` prompt at `:623` already knows this and says *"Write 2-6 dense
     sentences in third person"* alongside the character limit.
     `extract_summaries_batch` at `:519` gets the character count without the
     sentence guidance.

   Both are upstream-library text, so this is a `dedup_guard`-style patch rather than
   a fork. **Worth trying before anyone pays to regenerate anything:** it is free, it
   would make §6a's (c) and (e) unnecessary, and unlike them it fixes the *pipeline*
   rather than buying around it. (Not a `maxLength` in the schema: under constrained
   decoding that truncates mid-word, which is strictly worse than the
   `truncate_at_sentence` already applied — and is the same "stop abruptly" defect
   §2d refuses to train on.)
3. **The 267-out-of-range figure in `contradiction_gate.py:24-27` should be
   annotated**: it is a pre-contradiction-gate measurement, and post-gate the same
   model over 2,173 calls produced zero. The invariant the comment defends is still
   right; the number is now historical.
4. **`graphiti_client._bound_index_arrays:96-98` still says "three such fields"**
   where there are four (§4's incidental finding, still unfixed — this task does not
   touch `src/`). Its "Observed twice" note could also now carry a rate.

## Addendum 2026-09-17: the summaries question, settled by measurement

§6a offered three options for `extract_summaries_batch`, whose targets were 88%
rejected for exceeding `MAX_SUMMARY_CHARS`. A controlled probe settles it, and the
answer is none of the three.

**The prompt fix does not work.** The diagnosis looked sound: `extract_summaries_batch`
gives a bare character budget, while its sibling `extract_summary`
(`prompts/extract_nodes.py:623`) pairs the same limit with *"Write 2-6 dense sentences in
third person."* Patching the batch prompt to match, then replaying the SAME 25 captured
prompts through both variants against the cheap tier:

| arm | calls | summaries | over 1,000 chars | median | max |
|---|---:|---:|---:|---:|---:|
| original | 25 | 29 | **68.97%** | 1,979 | 11,079 |
| patched | 25 | 29 | **68.97%** | 1,706 | 18,322 |

Identical compliance. The median improved 14%, the max got 65% worse. The original arm's
68.97% matches the full capture's 69.2%, so 25 prompts is representative, and both arms
hit the same 5 call errors. 50 calls, well under $1. **The patch was not shipped.**

**Because the limit was never the model's job.** `node_operations.py:1000` applies
`truncate_at_sentence(summarized_entity.summary, MAX_SUMMARY_CHARS)` to every summary.
The limit is advisory in the prompt and enforced by post-processing. No model respects it
— solar-pro4 69.2%, gpt-5-mini 52.9%, patched solar-pro4 68.97% — and the pipeline has
always coped.

**So rejecting those 213 targets was over-strict.** They are not wrong answers; they are
the pipeline's normal, tolerated output. Rebuilt with `--allow-overlong-summaries`:
`extract_summaries_batch` goes from **19 distinct examples to 189**, and every prompt
lands within ~4 points of `TARGET_MIX` (most within 2). A model trained on these behaves
exactly as production does today, and graphiti truncates its output identically.

The `--allow-overlong-summaries` build is now the shipped one. The stricter build remains
available for comparison.
